Key files that must stay in sync:

  - Environment variable AI_VL_SCENE_JSON for scene selection (Manim is a

  - Never run ffmpeg if Manim failed (it will silently use the stale render)
  - Render flags during refinement: -qh --flush_cache --disable_caching

SECTION 3 — THE SCENE DESIGN PROTOCOL (READ THIS FOR EVERY NEW SCENE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Before writing a single JSON key, answer these questions explicitly:

  Q1. What is the ONE conceptual question this scene answers?
      Write it as a single sentence. If you cannot, the scene is not ready.

  Q2. What visual metaphor carries the scene from beginning to end?
      It should be ONE object or system that evolves — not a series of
      unrelated elements appearing and disappearing.

  Q3. What is the opening visual? (No dead blank screen allowed.)
      The first frame must have visual intent.

  Q4. What is the closing visual? (No abrupt black screen with audio still on.)
      The last frame must feel resolved.

  Q5. What is the attention arc?
      Know in advance where the viewer's eye should travel through the scene.

  Q6. At what moments does the narration shift conceptually?
      Those are the ONLY moments that justify a major visual change.

If you can answer all six cleanly — proceed to the beat map.
If you cannot — stop. Think first. The beat map will be wrong if the
thinking is wrong.

SECTION 4 — THE VISUAL GRAMMAR (WHAT GOOD LOOKS LIKE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

MOTION GRAMMAR:
  The 3Blue1Brown principle: motion IS the explanation.
  If you can remove the motion and the concept still lands — the motion was
  decorative. Every animated transition must earn its place by teaching something.

  Evolve > Transform > Resolve
  NOT: Show > Hold > Remove > Show Next

  Transform existing objects into new states when the concepts are related.
  Never destroy and recreate what could be morphed.
  Motion must carry meaning. Decoration is not motion.
  Avoid static holds longer than ~0.5-1.0s unless intentionally dramatic.
  Ask before every transition: does this motion explain the idea, or just
  move things around? If it just moves things — redesign it.

DENSITY GRAMMAR:
  3Blue1Brown scenes feel spacious because restraint is a design decision.
  Complexity is earned gradually — never dumped on screen at once.

  Max 2-3 active visual elements at any moment.
  One dominant focal element always. Secondary elements must be subdued.
  No text clutter. No overlapping layers unless designed.
  When in doubt — remove it. Then ask if you even need what remains.
  Negative space is not a failure to fill the screen. It is focus.

LAYOUT GRAMMAR:
  There is no layout template. There is no reference sheet. There is no cage.

  Every scene earns its own composition from the concept it is trying to teach.
  The script tells you what the idea is. The idea tells you what the space
  needs to look like. You design from concept outward — not from a grid inward.

  Ask for every scene:
    - What spatial relationship best represents this idea?
    - Where should the viewer's eye start, and where should it end?
    - What does the composition feel like at the opening frame?
    - What does it feel like at the closing frame?
    - Does the layout evolve as the concept evolves, or does it stay fixed?

  Design rules that always apply regardless of composition:
    - One dominant focal element at all times
    - Visual weight must be intentional — nothing sits somewhere by accident
    - Negative space is an active design choice, not leftover emptiness
    - If two elements compete for attention, one of them is wrong
    - The composition of the final frame is the most important frame to design

  Available zones as technical anchors for the renderer:
    title / center / left / right / bottom / left-center / center-right /
    center_span
  Use these as positioning handles — not as a layout system to conform to.

TYPOGRAPHY GRAMMAR:
  Hierarchy: title > main text > supporting text
  No long paragraphs on screen.
  Text must be minimal and purposeful.
  Titles should be removed once they have served their purpose.

CONTINUITY GRAMMAR:
  Scene grammar must be consistent with Scene 1.
  Later scenes must feel like they belong to the same system.
  Pacing, density, and motion decisions should match Scene 1's philosophy
  unless there is a specific, justifiable reason to deviate.
  Never drift accidentally. Drift only with intent.

SECTION 5 — FAILURE PATTERNS (NAME THEM, CATCH THEM EARLY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SLIDE BEHAVIOR — the most common failure.
  Symptom: show text > wait > remove > show next text > repeat
  Cause: treating the scene as a slideshow
  Fix: replace every hold with an evolution or transformation

DEAD SCENE — visuals feel frozen and lifeless.
  Symptom: viewer has nothing to follow
  Cause: large offsets, excessive waits, no transforms
  Fix: shorten durations, increase transform usage, reduce idle time

OBJECT DRIFT — elements wander off-screen or feel displaced.
  Symptom: objects slowly move to wrong positions over time
  Cause: repeated micro-motion shifts compounding
  Fix: control or disable micro-motion during transform-heavy sequences

SCENE GRAMMAR DRIFT — later scenes feel like a different project.
  Symptom: inconsistent pacing, different visual density, foreign style
  Cause: not comparing to Scene 1 before finalizing the new scene
  Fix: before accepting any scene, compare it to Scene 1

STALE RENDER TRAP — changes appear to have no effect.
  Symptom: video unchanged despite code changes
  Cause: Manim cache reuse
  Fix: always use --flush_cache --disable_caching during active refinement

AUDIO DRIFT — visuals lag behind or ahead of narration.
  Symptom: narration mentions X, visual of X is already gone or has not appeared
  Cause: timestamps not regenerated after any audio change
  Fix: regenerate timestamps after every audio modification

FFMPEG GHOST — final video unchanged despite a fresh Manim render attempt.
  Symptom: the old video is still there even though you ran the pipeline
  Cause: Manim failed silently; ffmpeg reused the old file
  Fix: check Manim exit code before running ffmpeg

ARCHITECTURE REFLEX — treating scene dissatisfaction as an engine problem.
  Symptom: urge to restructure schema, refactor renderer, or rewrite pipeline
  Cause: scene craft problem misidentified as technical problem
  Fix: the engine is stable. fix the scene, not the system.

CLOSING SCENE SUMMARY TRAP — final scene recaps instead of resolves.
  Symptom: last scene feels like a credits roll or a bullet-point review
  Cause: treating the final scene as a summary rather than an arrival
  Fix: the final scene must deliver a new feeling, not repeat old information.
  The viewer has watched everything. Give them somewhere to land, not a list
  of what they just saw.

SECTION 6 — ITERATION DISCIPLINE (HOW TO REFINE WITHOUT WASTING A WEEK)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The reason scenes take a week is not complexity. It is iteration drift:
fixing the wrong thing, fixing too many things at once, or re-fixing things
that were already acceptable.

STRICT ITERATION PROTOCOL:
  1. Isolate ONE specific visual segment or ONE scene-level weakness
  2. Name the failure type exactly (pacing / motion / metaphor / hierarchy /
     continuity / timing / density)
  3. Make the MINIMAL change that addresses it
  4. Render with --flush_cache --disable_caching
  5. Evaluate ONLY that change — nothing else

WHAT NOT TO DO:
  - Never refactor the whole scene per iteration pass
  - Never change multiple subsystems in one move
  - Never treat every visual disappointment as an architecture problem
  - Never cycle between minor adjustments without a structural insight
  - Never reopen a scene that is at 90%+ correctness just because the next
    scene feels harder

TARGET STATE PER FIRST PASS: 85-90% correctness.
  Not perfection. Get the concept, hierarchy, and flow right from the start.
  Minor alignment and polish issues are deferred to a batch pass later.
  The first pass that requires 5+ iterations to reach 85% means the
  Scene Design Protocol (Section 3) was skipped or rushed.

SECTION 7 — SCENE COMPLETION CRITERIA (SHIP WHEN ALL PASS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A scene is production-ready when all of the following are true:
  [ ] No dead blank time at the start
  [ ] No static holds longer than ~1s without visual intent
  [ ] One dominant focal element present at all times
  [ ] Transitions feel continuous — not slide-like replacements
  [ ] Visuals evolve in sync with narration
  [ ] Viewer attention is guided naturally by motion and hierarchy
  [ ] No visual clutter or unintentional overlap
  [ ] Ending feels resolved — not abrupt
  [ ] Scene feels consistent with Scene 1's visual grammar
  [ ] No stale cache artifacts
  [ ] Timestamps regenerated from actual WAV durations
  [ ] Schema, actions, and renderer are in sync

If any fail — scene is not done.
If all pass — ship it and move forward.
