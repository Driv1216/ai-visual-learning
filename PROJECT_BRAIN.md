# Project Context Document (PCD) — ai-visual-learning

## 1. Project Overview

### What this project is
This project is a reusable, scalable educational video generation system built to produce high-quality technical explainer videos. The immediate use case is a foundational Machine Learning course, but the architecture is intentionally designed to support future courses in Deep Learning, NLP, and other technical subjects.

It is not just a single Manim animation project. It has evolved into a structured pipeline that combines:
- script writing
- scene-level planning
- structured scene metadata
- AI voice generation
- audio segmentation
- timestamp generation
- timeline-driven animation
- final audio-video assembly

The repository name chosen for this system is:

`ai-visual-learning`

### Purpose and vision
The vision is to create educational content that feels closer to premium intuition-first explainers rather than standard tutorial slides. The intended output should feel visually intelligent, conceptually elegant, tightly synchronized, and engaging enough to sustain attention over entire lessons.

The larger goal is to create an extensible framework that allows multiple courses to be built under one system, with reusable core logic and course-specific content assets.

### Target audience
The target audience is:
- beginners
- first-year engineering students
- people with basic Python familiarity
- learners with low to moderate mathematical maturity
- viewers who need conceptual clarity before formalism

The content should not feel childish, but it should remain approachable and not excessively derivation-heavy.

## 5. System / Workflow Architecture

This project converged on a **timeline-driven, spec-driven pipeline**.

### High-level pipeline
The intended workflow is:

1. idea / curriculum planning
2. script writing
3. scene segmentation
4. JSON scene specification
5. narration audio generation per segment
6. scene audio concatenation
7. timestamp generation from actual audio durations
8. JSON-driven Manim render
9. audio-video muxing
10. future final video assembly across scenes

### Stage-by-stage detail

#### Stage 1 — curriculum planning
This stage determines:
- course scope
- video order
- scene order
- narrative flow
- duration targets
- pedagogical progression

This is where the user decides what topics the course will cover and how they should build conceptually.

#### Stage 2 — script writing
The user writes the narration text in prose.

Then the narration is broken into:
- videos
- scenes
- scene-level narration segments

The project has already established that one large narration block is too hard to sync well. Segmenting the narration is necessary.

#### Stage 3 — scene specification
Each scene is represented as structured JSON containing:
- `scene_id`
- `video_title`
- `scene_title`
- `order`
- `voice`
- `narration`
- `visual_timeline`
- `notes`

Later refinements added more structure to visual steps:
- `zone`
- `transition_in`
- `transition_out`
- `persist`
- `replace`
- `duration`
- `camera_scale`

The scene JSON is meant to be the single source of truth for scene behavior.

#### Stage 4 — audio generation
Audio is generated **per narration segment**, not as one monolithic clip.

Benefits established in the project:
- easier retries
- easier debugging
- easier re-generation of only changed lines
- better timestamping
- better sync control

Output:
- one WAV file per narration segment

Example target directory:
`courses/machine-learning/generated/audio_segments/<scene_id>/`

#### Stage 5 — audio concatenation
All segment WAV files for a scene are concatenated into a single full scene WAV.

Why this matters:
- creates a clean scene audio master
- preserves true timing
- supports final muxing
- keeps segment-level and scene-level outputs both available

#### Stage 6 — timestamp generation
Timestamps are derived from actual segment WAV durations.

The timestamp file should include entries like:
- `id`
- `text`
- `start`
- `end`
- `duration`

The timestamp file must be compatible with the renderer and should be a list of dictionaries, not an arbitrary object shape.

This is a critical part of the architecture because it creates the shared timing clock between narration and animation.

#### Stage 7 — rendering
The renderer:
- loads the scene JSON
- loads the timestamp file
- sorts visual steps by anchor time + offset
- maps actions to Manim objects and animations
- maintains zone-aware state
- manages replacement and persistence rules

The renderer is driven by:
- scene JSON
- timestamp JSON
- action engine
- environment variable pointing to scene JSON

#### Stage 8 — muxing
After a successful Manim render, ffmpeg combines:
- rendered scene video
- scene WAV

Important workflow lesson learned:
**Do not run ffmpeg if Manim failed.**
Otherwise ffmpeg may reuse a stale render and create misleading output.

#### Stage 9 — future scene/course merge
Not fully built yet, but intended:
- combine multiple scene videos into full video
- eventually handle full course assembly

### Core architectural principle
This principle is central:

**Content is data. Rendering is code.**

Scene logic should not be hardcoded inside bespoke scene classes unless absolutely necessary.

## 7. Key Decisions Made

### Decision: one main repo, not many repos
**Decision:** Keep all related course work inside one main repository with modular folder structure.

**Reasoning:**  
Makes the system scalable across ML, NLP, DL, and future courses while keeping reusable engine code centralized.

### Decision: JSON-driven scenes
**Decision:** Scene content should live in structured JSON rather than ad hoc Manim code.

**Reasoning:**  
Allows validation, reuse, scaling, and clear separation of content planning from rendering logic.

### Decision: schema validation via Pydantic
**Decision:** Use `SceneSpec` and related Pydantic models.

**Reasoning:**  
Prevents malformed scene specs, catches invalid actions, enforces consistency, and gives predictable structure to the pipeline.

### Decision: use segment-wise narration audio
**Decision:** Generate one audio file per narration segment.

**Reasoning:**  
Supports retries, timestamp generation, fine-grained control, and better synchronization.

### Decision: use WAV as the working/master format
**Decision:** The pipeline uses WAV for segment and scene audio.

**Reasoning:**  
Sarvam returns WAV data. WAV is also better for editing, concatenation, and reliable timing.

### Decision: derive timestamps from actual audio durations
**Decision:** Timestamp files are generated using the real durations of segment WAV files.

**Reasoning:**  
Creates deterministic sync and avoids guessed or manually estimated timings.

### Decision: use environment variable for scene selection
**Decision:** The renderer loads scene JSON path via `AI_VL_SCENE_JSON`.

**Reasoning:**  
Manim launches a fresh process, so runtime Python state from a previous script call cannot be relied upon.

### Decision: zone-based layout
**Decision:** Use zones such as `title`, `center`, `bottom`, `left`, `right`.

**Reasoning:**  
Prevents uncontrolled overlap and makes the scene composition more structured.

### Decision: action engine abstraction
**Decision:** Use an action system in `actions.py` rather than hardcode each scene.

**Reasoning:**  
Makes the visual engine reusable across multiple scenes and courses.

### Decision: iterative refinement in passes
**Decision:** Refine in phases rather than trying to reach premium output in one shot.

**Reasoning:**  
Separates:
- engine stability
- scene intelligence
- cinematic polish

This reduces chaos during debugging and lets each layer improve deliberately.

### Decision: use cache-flush and no-caching during refinement
**Decision:** During active iteration, render with:
`--flush_cache --disable_caching`

**Reasoning:**  
Prevents stale render confusion and false conclusions about whether changes actually took effect.

### Decision: lock Scene 1 as the reference scene instead of endlessly reworking it
**Decision:** Stop casually reopening Scene 1 once it becomes stable enough, and use it as the reference grammar for later scenes.

**Reasoning:**  
A project like this cannot scale if the first scene is endlessly relitigated. Once Scene 1 reached a stable, satisfactory level, it became more valuable as a style anchor than as an infinite refinement target.

### Decision: move forward to Scene 2 while preserving Scene 1 grammar
**Decision:** Advance to Scene 2 rather than continuing to spend project energy only on Scene 1.

**Reasoning:**  
The next major challenge is consistency across scenes, not isolated optimization of one scene. The project now needs to prove that the visual language can carry forward.

### Decision: treat future scene work as extension, not rescue
**Decision:** Assume the pipeline already works and that new scene work should focus on structure, pacing, and elegance.

**Reasoning:**  
This changes the working posture from “make the engine survive” to “make scenes feel premium.”

## DO NOT TOUCH (STABLE SYSTEMS)

- Audio pipeline (WAV-based)
- Timestamp generation logic
- JSON-driven scene architecture
- Schema-action-renderer contract
- segment-wise narration workflow
- environment-variable-based scene selection

Unless there is a clear, critical failure.

## ITERATION STRATEGY

All improvements follow:

1. Isolate one visual segment or one scene-level weakness
2. Identify failure type:
   - pacing
   - motion
   - metaphor
   - hierarchy
   - continuity
   - timing
3. Apply minimal targeted change
4. Render with cache disabled
5. Evaluate only that change

Do NOT:
- refactor entire scenes per iteration
- change multiple subsystems at once
- treat every dissatisfaction as an architecture problem

## ITERATION DISCIPLINE

- Do not repeatedly tweak the same scene beyond diminishing returns
- If a scene is functionally correct, move forward
- Fixes can be applied later in a batch refinement pass
- Avoid cycling between minor adjustments without structural change

Scene 2 established the importance of forward momentum over perfection.

## SCENE COMPLETION CRITERIA

A scene is considered “production-ready” when:

- no dead time at start
- no long static holds
- one clear focal element at all times
- transitions feel continuous, not slide-like
- visuals evolve with narration
- viewer attention is guided naturally
- no clutter or overlap
- ending feels resolved (not abrupt)
- the scene feels consistent with the established visual grammar of the project

If any of the above fail → scene is not done

## 13. ENGINE CONTRACT (NON-NEGOTIABLE)

The rendering engine MUST guarantee the following behaviors at all times.

These are not suggestions. These are invariants.

### 1. Timeline Integrity
- Every visual step MUST be anchored to a valid narration segment ID
- Visual execution time MUST be derived from timestamps, not guessed
- No visual step should execute outside the timeline unless explicitly allowed

### 2. Zone Discipline
- Only one active object per zone unless explicitly overridden
- Replacing an object MUST remove the previous object in that zone
- No uncontrolled stacking of objects

### 3. Object Lifecycle
Every object must follow:
- creation → (optional transforms) → removal OR persistence

No object should:
- remain indefinitely without intent
- become orphaned
- overlap unintentionally

### 4. Replace Semantics
If `"replace": "<zone>"` is used:
- previous object MUST be removed BEFORE new object is added
- transitions must be smooth (Transform preferred over FadeOut+FadeIn when conceptually related)

### 5. Synchronization
- Visual timing MUST match narration timing
- No visual should significantly lag behind narration
- No visual should appear too early relative to speech

### 6. Determinism
Given:
- same scene JSON
- same timestamps
- same code

Output MUST be identical (no randomness unless explicitly defined)

### 7. Failure Safety
- If timestamps are invalid → rendering must fail fast
- If scene schema is invalid → validation must fail
- No silent fallback behavior

## 14. VISUAL STANDARD (QUALITY BAR)

This defines what “good” means visually.

Any scene that violates this is considered substandard.

### 1. Focus Rule
- At any moment, there must be ONE dominant focal element
- Secondary elements must be visually subdued

### 2. Motion Rule
- Motion must convey meaning, not decoration
- Prefer transformation over replacement
- Avoid static holds longer than ~0.5–1.0s unless intentional

### 3. Density Rule
- Maximum 2–3 active visual elements at once
- Avoid text clutter
- Avoid overlapping layers unless designed

### 4. Evolution Rule
Scenes must feel like:
- ideas evolving
NOT:
- slides appearing/disappearing

### 5. Continuity Rule
- Objects should persist and transform when conceptually related
- Avoid destroying and recreating the same idea visually

### 6. Timing Rule
- Visual changes should align with narration emphasis
- Important words → visual changes

### 7. Typography Rule
- Use hierarchy: title > main text > supporting text
- Avoid long paragraphs
- Keep text minimal and purposeful

### 8. Cinematic Rule
Scenes should feel:
- intentional
- smooth
- controlled

NOT:
- jittery
- mechanical
- script-driven

### 9. Scene-to-scene consistency rule
- Later scenes must feel like they belong to the same system
- Changes in visual grammar should be intentional, not accidental drift

---


## COMPOSITION RULES

- Elements that form a concept MUST be treated as a single composition
- Avoid placing related elements in distant independent zones unless intentionally separated
- Maintain visual balance:
  - left vs right
  - top vs bottom
- Avoid:
  - overcrowding one side
  - oversized elements dominating composition
  - misaligned visual centers
  - weak grouping of related elements

A composition should feel visually centered and balanced, not zone-scattered.

## 15. COMMON FAILURE MODES

These are known recurring issues during development.

### 1. Stale Render Issue
Symptom:
- video does not reflect changes

Cause:
- Manim cache reuse

Fix:
- use `--flush_cache --disable_caching`

---

### 2. Audio Mismatch
Symptom:
- visuals not synced with narration

Cause:
- timestamps not regenerated after audio change

Fix:
- regenerate timestamps after any audio change

---

### 3. Wrong Audio Format
Symptom:
- corrupted or unreadable audio

Cause:
- treating WAV as MP3

Fix:
- always use `.wav` internally

---

### 4. ffmpeg Using Old Video
Symptom:
- final video unchanged despite render changes

Cause:
- Manim render failed but ffmpeg still ran

Fix:
- never run ffmpeg if Manim fails

---

### 5. Static / Dead Scene
Symptom:
- visuals feel stuck

Cause:
- large offsets
- excessive waits
- lack of transforms

Fix:
- reduce offsets
- shorten durations
- increase transform usage

---

### 6. Object Drift
Symptom:
- objects slowly move off-screen or feel accidentally displaced

Cause:
- repeated micro-motion shifts

Fix:
- disable or control unnecessary micro-motion during transform-heavy sequences

---

### 7. Slide-like Output
Symptom:
- feels like PowerPoint

Cause:
- show → hold → remove pattern

Fix:
- replace with:
  evolve → transform → resolve

---

### 8. Scene Grammar Drift
Symptom:
- later scenes feel like a different project

Cause:
- inconsistent pacing, density, or motion decisions

Fix:
- compare against Scene 1 reference grammar before accepting the scene

### 1. One Idea Per Scene

“What is the limitation of rule-based systems?”

### 2. Visuals Must Justify Themselves

- support narration
OR

### 3. No Idle Visuals

- evolve
- transform
- fade

---

### 4. Prefer Transformation Over Replacement
Bad:
- remove object → show new object

Good:
- transform existing object into new state

---

### 5. Narration Drives Motion

- emphasis
- transitions in explanation
- conceptual shifts

---

### 6. Reduce Cognitive Load
Avoid:
- too many elements
- too many colors
- too many simultaneous ideas

---
